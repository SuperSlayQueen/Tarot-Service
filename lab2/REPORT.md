## Часть A. Таблица `lab2_events`

### Задание 1–3. Размер при росте

| Количество строк | Размер таблицы | Общий размер (с PK) |
|-----------------:|----------------|---------------------|
| 10 000 | 672 kB | 944 kB |
| 100 000 | 6672 kB | 8912 kB |
| 1 000 000 | 65 MB | 87 MB |
| 5 000 000 | 326 MB | 433 MB |

Размер растёт примерно линейно с числом строк.

### Задание 4. SELECT без индекса `WHERE user_id = 123`

| Строк | Scan | Execution Time |
|------:|------|----------------|
| 10 000 | Seq Scan | 0.306 ms |
| 100 000 | Seq Scan | 4.185 ms |
| 1 000 000 | Parallel Seq Scan | 18.207 ms |
| 5 000 000 | Parallel Seq Scan | **82.795 ms** |

**Вывод:** без индекса время растёт вместе с объёмом таблицы (нужно просмотреть почти все строки/страницы).

### Задание 5. После `CREATE INDEX idx_lab2_events_user_id`

На таблице 5M:

| | Без индекса | С индексом |
|--|-------------|------------|
| Scan | Parallel Seq Scan | Bitmap Index/Heap Scan |
| Time | 82.8 ms | **~0.11–0.22 ms** |

Разница становится огромной уже на миллионах строк. Индекс — не всегда оптимален (широкие выборки), но для точечного `user_id` обязателен.

### Задание 6. Диапазон дат

`WHERE created_at >= now() - 1 day`:

| | Time | Scan |
|--|------|------|
| До индекса | 201.7 ms | Parallel Seq |
| После `idx_lab2_events_created_at` | **43.2 ms** | Bitmap |

Узкий диапазон выигрывает от индекса; если бы условие покрывало большую долю года, планировщик мог бы снова выбрать Seq Scan.

### Задание 7. Фильтр + сортировка + LIMIT

```sql
SELECT * FROM lab2_events
WHERE user_id = 123
ORDER BY created_at DESC
LIMIT 100;
```

Составной индекс `(user_id, created_at DESC)` удерживает время ~**0.15 ms**.  
Порядок колонок критичен: сначала равенство, затем сортировка.

### Задание 8. Агрегация

```sql
SELECT event_type, COUNT(*)
FROM lab2_events
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY event_type;
```

Execution Time ≈ **136 ms** (Sort/Aggregate по большому срезу).  
Индекс по `created_at` сужает вход, но **не убирает** стоимость группировки множества строк. Одного индекса недостаточно для тяжёлой аналитики.

### Задание 9–10. Цена индексов и их размер (на 5M)

| Индекс | Размер |
|--------|--------|
| `lab2_events_pkey` | 107 MB |
| `idx_lab2_events_user_id` | 34 MB |
| `idx_lab2_events_created_at` | 107 MB |
| `idx_lab2_events_user_created` | 150 MB |

Итого вторичные индексы сопоставимы с самой таблицей (326 MB table → total ~724 MB с индексами).

**Измерение INSERT 200k** (таблица `lab2_write_bench`):

| | Время |
|--|------:|
| Без доп. индексов | **0.348 s** |
| С 3 индексами (`user_id`, `created_at`, `(user_id, created_at DESC)`) | **1.176 s** (~3.4×) |

**10 000 000 строк** не генерировали (по заданию — опционально при нехватке места/времени); контрольные точки до 5M выполнены.

### Задание 11. Когда индекс уже не спасает?

Запрос вида `GROUP BY DATE(created_at)` за год на 100M строк:

1. Даже с индексом по `created_at` нужно прочитать/агрегировать огромный объём.
2. Функция `DATE(created_at)` мешает простому Index Only / range использованию.
3. Индекс не даёт «мгновенный» ответ на аналитику полного периода.
4. Дальше: партиционирование по времени, rollup/материализованные представления, OLAP, пред агрегаты, BRIN на append-only логах.

## Часть B. Собственный сервис (`readings`)

### Задание 12. Сущность

- **readings** — сессии гадания.
- Сейчас в эксперименте: до **1 000 000** строк.
- Растёт с каждым запросом пользователя; идеальный кандидат для масштабирования и partitioning (Lab 3).

### Задание 13–16. Запросы и сравнение объёмов

| Запрос | 100k | 1M | **5M** | Наблюдение |
|--------|------|----|--------|------------|
| Q1 `WHERE user_id=1` | 22.4 ms | 93.4 ms | **564 ms** | Сильно растёт (много строк user_id=1 + Append) |
| Q2 range `created_at` 7 days | 3.7 ms | 7.1 ms | **29.5 ms** | Pruning помогает, но объём окна растёт |
| Q3 `user_id ORDER BY created_at LIMIT 50` | 0.26 ms | 0.22 ms | **0.21 ms** | Стабильно за счёт index + LIMIT |

### Задание 17. Узкое место

Сильнее всего от роста зависит **Q1** (выгрузка всех readings пользователя без LIMIT): на 1M уже ~93 ms и Bitmap/Seq по нескольким партициям, включая `readings_default` с большой долей «старых» данных.

### Задание 18. Улучшение

1. Для UI всегда использовать **LIMIT/keyset pagination** (Q3-паттерн) — уже в API.
2. Составной индекс `(user_id, created_at DESC)` / `(user_id, status, created_at DESC)` — в миграциях Lab 1.
3. Партиционирование по `created_at` + не складывать историю в DEFAULT (Lab 3).

### Задание 19. Граница применимости индексов (по измерениям)

При объёме около **5 млн** `readings` запрос «все записи пользователя без LIMIT» занимает **~564 ms** даже с индексом по `user_id` (≈2.5M actual rows + Append по партициям).  
Тот же доступ с `ORDER BY created_at DESC LIMIT 50` остаётся **~0.2 ms**.  
Вывод: индекс решает точечный/ограниченный доступ, но не спасает от чтения огромного результата. Дальше — LIMIT/keyset, партиционирование без раздутого DEFAULT, при аналитике — другие модели хранения.
