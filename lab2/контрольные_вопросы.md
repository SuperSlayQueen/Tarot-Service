# Контрольные вопросы — Лабораторная работа №2
# Когда индексов недостаточно: рост данных

## 1. Почему Seq Scan не всегда плохой план?

При чтении большой доли таблицы последовательное чтение дешевле случайного I/O по индексу. Планировщик выбирает минимальный cost, а не «красивый» Index Scan.

## 2. Почему PostgreSQL может не использовать существующий индекс?

Низкая селективность, неверное выражение/порядок колонок, устаревшая статистика, оценка что Seq Scan дешевле.

## 3. Что происходит с индексом при INSERT?

Для каждой новой строки ключ вставляется в структуру индекса (B-Tree и др.). Это доп. CPU, I/O и WAL.

## 4. Почему много индексов замедляет запись?

Каждый INSERT/UPDATE/DELETE обновляет все затронутые индексы. Чем их больше — тем дороже запись.

## 5. Что такое селективность?

Доля строк, подходящих под условие фильтра. Чем меньше доля — тем полезнее индекс.

## 6. Почему индекс хорош для небольшой части таблицы?

Индекс быстро находит мало TID’ов; стоимость random heap reads остаётся приемлемой.

## 7. Почему индекс менее полезен, если запрос возвращает большую часть таблицы?

Нужно прочитать почти все страницы через индекс (часто хуже, чем один Seq Scan).

## 8. Зачем нужен EXPLAIN ANALYZE?

Чтобы измерить реальный план и время до/после изменений, а не гадать по наличию индекса.

## 9. Что означает Rows Removed by Filter?

Сколько строк прочитано и отброшено фильтром (типично при Seq Scan / heap scan с Filter).

## 10. Что означает Index Cond?

Условие, применённое при просмотре индекса (поиск по ключу), в отличие от Filter на этапе heap.

## 11. Чем Index Scan отличается от Bitmap Index Scan?

Index Scan идёт по индексу и сразу за строками (хорошо для малого числа строк). Bitmap собирает множество TID и читает heap пакетом (лучше для среднего объёма / нескольких индексов).

## 12. Почему важен порядок колонок в составном индексе?

Префиксное правило B-Tree: без ведущей колонки индекс часто неприменим.

## 13. Почему GROUP BY может оставаться дорогим даже с индексом?

Нужно агрегировать много строк; индекс может сузить диапазон, но HashAggregate/GroupAggregate всё равно обрабатывает большой объём.

## 14. Как статистика влияет на выбор плана?

`pg_statistic` / NDV / MCV определяют оценки rows → выбор Seq/Index/Bitmap/join order. После больших загрузок нужен `ANALYZE`.

## 15. Что происходит с производительностью при росте таблицы?

Без индекса время фильтров растёт roughly линейно с размером. С индексом точечные запросы стабильнее, но range/agg и размер индекса тоже растут.

## 16. Почему нельзя создавать индексы на все колонки?

Цена хранения и записи; часть индексов бесполезна для реальных запросов.

## 17. Как определить размер таблицы?

```sql
SELECT pg_size_pretty(pg_relation_size('events'));
SELECT pg_size_pretty(pg_total_relation_size('events'));
```

## 18. Как определить размер индекса?

```sql
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE relname = 'events';
```
