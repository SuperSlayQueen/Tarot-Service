# Контрольные вопросы — Лабораторная работа №3
# Партиционирование PostgreSQL

## 1. Что такое partitioning?

Физическое разделение одной логической таблицы на несколько секций (партиций) по ключу, при этом для приложения таблица выглядит единой.

## 2. Чем partitioning отличается от индекса?

Индекс ускоряет поиск строк внутри набора данных. Партиционирование уменьшает объём данных, которые вообще нужно рассматривать (и упрощает обслуживание: drop старых секций). Это разные уровни оптимизации.

## 3. Какие стратегии поддерживает PostgreSQL?

RANGE, LIST, HASH (declarative partitioning). Также возможны многоуровневые (subpartition) схемы.

## 4. Когда использовать RANGE?

Естественные диапазоны: даты, числовые интервалы, когда часто фильтруют `BETWEEN` / `>= ... < ...` и нужно удалять старые данные целиком.

## 5. Когда использовать LIST?

Дискретные категории: тип клиента, страна, tenant, статус с небольшим числом значений.

## 6. Когда использовать HASH?

Нужно равномерно размазать нагрузку/данные без естественного диапазона; запросы часто по ключу хеширования (`user_id = ?`).

## 7. Как выбрать partition key?

По колонке, которая: (1) есть в большинстве тяжёлых фильтров, (2) даёт полезный pruning, (3) соответствует жизненному циклу данных (архивация/удаление).

## 8. Что такое partition pruning?

Исключение ненужных партиций на этапе планирования/выполнения, если условие запроса ограничивает partition key.

## 9. Почему pruning может не сработать?

Нет условия по ключу партиционирования; ключ обёрнут в функцию; параметр не константный для planner; неверный тип сравнения.

## 10. Можно ли использовать индексы вместе с partitioning?

Да. Индексы создаются на parent и локально существуют на каждой партиции. Pruning + index часто сильнее, чем только один механизм.

## 11. Что будет, если подходящей партиции нет?

INSERT падает с ошибкой (если нет DEFAULT partition). Поэтому нужны заранее созданные будущие партиции или DEFAULT (с оговорками).

## 12. Зачем создавать будущие партиции заранее?

Чтобы ночные/утренние INSERT не падали, когда наступает новый день/месяц.

## 13. Почему создание партиций должно быть автоматизировано?

Ручное создание не масштабируется и легко забывается → инциденты в production.

## 14. Чем логирование ошибки отличается от alerting?

Лог можно не заметить. Alert активно уведомляет дежурного о проблеме до пользовательского сбоя.

## 15. Что такое recovery alert?

Уведомление, что проблема устранена (после CRITICAL пришло OK) — закрывает инцидент.

## 16. Почему нельзя бесконечно слать одинаковый alert?

Шум, усталость дежурных, потеря реакции на реальные аварии. Нужна дедупликация до смены состояния.

## 17. Всегда ли partitioning ускоряет запросы?

Нет. Без pruning запрос сканирует все партиции (иногда хуже из‑за overhead). Неверный ключ/слишком мелкие или огромные партиции вредят.

## 18. Какие проблемы при неправильном размере партиций?

Слишком мелкие — тысячи партиций, тяжёлый planning. Слишком крупные — слабый pruning, долгий vacuum/maintenance одной секции.
