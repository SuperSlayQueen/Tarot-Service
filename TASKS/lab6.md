Лабораторная работа 6
Что происходит с backend-сервисом после шардирования
Цель работы
Понять, как шардирование изменяет работу обычных SQL-запросов и какие новые
проблемы появляются при распределении данных между несколькими PostgreSQL.
В работе необходимо проанализировать реальные запросы собственного backendсервиса и определить, какие из них могут выполняться на одном shard, а какие требуют
обращения к нескольким shard’ам.
1. Вспоминаем архитектуру
После шардирования:
 Backend
 │
 Router
 ┌───────┼───────┐
▼ ▼ ▼
 Shard 0 Shard 1 Shard 2
Router определяет, куда отправить запрос.
2. Single-Shard Query
Найдите в своём сервисе запрос, который после шардирования может быть выполнен
на одном shard.
Например, запрос с условием:
WHERE user_id = ?
если user_id является shard key.
Объясните, почему запросу не нужно обращаться к другим shard’ам.
3. Агрегирующий запрос
Найдите в своём сервисе запрос с агрегацией.
Например:

SUM
AVG
GROUP BY

shard’ами.
Например:

Shard 1 → result 150
Shard 2 → result 130
 ↓
 aggregation
 ↓
 400
Ответьте:
1. Можно ли выполнить такой запрос только на одном shard?
2. Где должны объединяться результаты?
3. Что происходит со временем выполнения при увеличении количества shard’ов?
4. JOIN между shard’ами
Найдите JOIN, который используется в вашем сервисе.
Например:
SELECT ...
FROM A
JOIN B ON ...
Определите, где находятся связанные данные.
Рассмотрите ситуацию:
Shard 0 Shard 1
Table A Table B
 │ │
 └──────── JOIN ──────┘
Ответьте:
1. Что произойдёт, если связанные записи находятся на разных shard’ах?
2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?
3. Какие данные пришлось бы передавать между shard’ами?
4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри одного
shard?

6. Отказ одного shard
Рассмотрите ситуацию:

Shard 1 ✓
Shard 2 ✗
Ответьте применительно к своему сервису:

7. Hot Shard
Представьте ситуацию:
Shard 0 → 10% запросов
Shard 1 → 15% запросов
Shard 2 → 75% запросов
Определите возможные причины:
• неудачный shard key;
• неравномерное распределение данных;
• популярный пользователь/tenant;
• определённый тип запросов.
Ответьте:
Почему равное количество строк на shard’ах ещё не означает равномерную
нагрузку?

На основании проведённого анализа ответьте на главный вопрос:
