# Контрольные вопросы — Лабораторная работа №4
# Primary + Replica / Read Scaling

## 1. Чем Primary отличается от Replica?

**Primary** принимает запись (INSERT/UPDATE/DELETE) и чтение.  
**Replica** — физическая копия Primary в режиме recovery: обслуживает SELECT, запись запрещена (`read-only transaction`).

## 2. Почему запись выполняем на Primary?

Только Primary — источник истины. Запись на Replica либо запрещена, либо (в multi-master) порождает конфликты. В схеме Primary–Replica все изменения идут на Primary, иначе копии разойдутся.

## 3. Как изменение из Primary попадает на Replica?

Primary пишет изменение в **WAL** → wal sender стримит WAL по сети → на Replica wal receiver принимает поток → standby применяет записи (replay) и становится копией Primary.

## 4. Что такое WAL в контексте репликации?

**Write-Ahead Log** — журнал упреждающей записи. Любое изменение сначала фиксируется в WAL. Для streaming replication Primary передаёт реплике не SQL-текст, а поток байт WAL; Replica «вечно восстанавливается» по этому потоку.

## 5. Что такое replication lag?

Задержка между моментом COMMIT на Primary и моментом, когда то же изменение уже применено (replay) на Replica. При асинхронной репликации lag обычно миллисекунды, но под нагрузкой/сетью может вырасти.

## 6. Почему SELECT сразу после INSERT на Replica может увидеть старые данные?

Потому что репликация **асинхронная** (у нас `sync_state = async`): приложение уже получило успех записи с Primary, а Replica ещё не догнала WAL. Это **eventual consistency**.

## 7. Что масштабируется при Read Scaling?

Не скорость одного SQL-запроса, а **пропускная способность системы по чтениям**: больше реплик → больше параллельных SELECT без перегрузки Primary. Один тяжёлый запрос на Replica сам по себе не станет быстрее.

## 8. Почему Replica не отменяет индексы и оптимизацию SQL?

Replica хранит те же данные и те же планы. Плохой Seq Scan на миллионах строк останется дорогим и на Replica. Read Scaling разгружает Primary, но не заменяет индексы, партиции и аккуратный SQL.

## 9. Расскажите про CAP-теорему

В распределённой системе нельзя одновременно гарантировать все три свойства:
- **C** Consistency — все узлы видят одни и те же актуальные данные;
- **A** Availability — каждый работающий узел отвечает;
- **P** Partition tolerance — система живёт при разрыве сети между узлами.

При network split приходится жертвовать C или A. Асинхронный Primary–Replica обычно выбирает **AP** с eventual consistency (возможен replication lag), а не строгую C на каждом чтении.
