# Контрольные вопросы — Лабораторная работа №1
# Индексы и EXPLAIN ANALYZE в PostgreSQL

## 1. Чем EXPLAIN отличается от EXPLAIN ANALYZE?

**EXPLAIN** только оценивает план: cost, estimated rows, выбранные операции — запрос не выполняется.  
**EXPLAIN ANALYZE** реально выполняет запрос и показывает actual time, actual rows, loops, Planning/Execution Time.

## 2. Почему EXPLAIN ANALYZE может выполняться значительно дольше?

Потому что он действительно читает данные, применяет фильтры, делает JOIN/Sort и т.д. Для тяжёлых запросов или DML без транзакционного отката это дорого по времени и I/O.

## 3. Чем отличаются estimated и actual rows?

Estimated — оценка планировщика по статистике (`ANALYZE`). Actual — реально возвращённые строки. Большой разрыв значит устаревшую/неточную статистику или неудачные предположения о корреляции.

## 4. Когда Sequential Scan эффективнее индекса?

Когда нужна большая доля таблицы (низкая селективность), таблица маленькая, или random I/O по индексу дороже sequential read. Seq Scan читает страницы подряд — это часто быстрее, чем тысячи случайных обращений к heap.

## 5. Почему PostgreSQL может не использовать существующий индекс?

Низкая селективность, несовпадение выражения (`LOWER(email)` vs индекс по `email`), неверный порядок колонок в составном индексе, устаревшая статистика, `LIKE '%x'`, функции над колонкой, оценка cost индекса выше Seq Scan.

## 6. Что такое селективность?

Доля строк, удовлетворяющих условию. Высокая селективность (мало строк) → индекс выгоден. Низкая (много строк) → часто Seq Scan / Bitmap Scan.

## 7. Что делает Bitmap Index Scan и Bitmap Heap Scan?

Bitmap Index Scan собирает bitmap TID’ов по индексу. Bitmap Heap Scan читает heap по этому bitmap, часто с упорядочиванием по страницам (меньше random I/O). Удобно при «среднем» числе строк или объединении нескольких индексов (`BitmapAnd`/`BitmapOr`).

## 8. Чем Index Only Scan отличается от Index Scan?

Index Scan: индекс → TID → чтение строки из таблицы.  
Index Only Scan: все нужные поля есть в индексе (и visibility map позволяет), heap почти не читается.

## 9. Зачем INCLUDE в индексе?

Добавляет non-key колонки в лист B-Tree без участия в сортировке ключа — помогает получить Index Only Scan для `SELECT` с дополнительными полями.

## 10. В чём преимущество partial index?

Индексирует только нужное подмножество (`WHERE status = 'NEW'`), меньше размер и дешевле поддержка при INSERT/UPDATE неподходящих строк.

## 11. Почему expression index нужен для `LOWER(email)`?

Обычный индекс по `email` не применяется к выражению `LOWER(email)`. Индекс должен совпадать с выражением в запросе.

## 12. Почему нельзя индексировать все колонки?

Индексы занимают место, замедляют INSERT/UPDATE/DELETE (нужно обновлять каждый индекс), увеличивают WAL и vacuum. Многие индексы почти не используются (`idx_scan = 0`), но всё равно стоят при записи.

## 13. Как порядок колонок влияет на составной индекс?

B-Tree используется слева направо. Индекс `(user_id, created_at)` помогает `WHERE user_id = ?` и `WHERE user_id = ? AND created_at > ?`, но не `WHERE created_at > ?` без `user_id`.

## 14. Почему индекс может убрать Sort?

Если порядок индекса совпадает с `ORDER BY` (включая DESC), PostgreSQL может читать уже отсортированные ключи и не делать отдельный Sort.

## 15. Можно ли считать индекс с idx_scan = 0 бесполезным?

Не всегда: мог использоваться редко (отчёты), недавно создан, статистика сброшена после restart, нужен для уникальности/FK. Перед удалением — анализ нагрузки и зависимостей.
