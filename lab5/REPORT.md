## 1. Сущность и ключ

Шардируются `readings` (гадания) и дочерние `reading_cards`.
Shard key — `user_id`: известен до INSERT, сохраняет историю пользователя на одном узле.
UPDATE API не меняет владельца; такая операция потребовала бы переноса данных.
Запросы с ключом: `GET /api/reading?userId=1`, `GET /api/users/1/readings`, POST гадания.
Поиск по одному id, общая лента и статистика требуют всех шардов.
Равномерность зависит от разнообразия пользователей и объёма их историй, не только числа строк.

## 3. Router внутри backend

`C:\Users\Ardor\Desktop\c_labs\Sharding\ShardRouter.cs`:
- mod: первые 32 бита MD5 строки ключа (invariant culture), остаток по количеству узлов;
- consistent: 64-битное кольцо, 100 точек `shard-S-vnode-V` на узел, бинарный поиск
  первой точки >= hash(key) и переход к первой точке после конца кольца.

| user_id | mod 3 | mod 4 | ring 3 | ring 4 |
|--------:|------:|------:|-------:|-------:|
| 1 | 1 | 0 | 2 | 2 |
| 2 | 2 | 1 | 1 | 3 |

MD5 используется для стабильного распределения, не для паролей.
Program включает ShardedReadingRepository/ShardedStatsRepository при Sharding:Enabled=true.
ShardConnections: timeout подключения 5 с, команд 15 с; fingerprint конфигурации проверяется
по таблице shard_topology при старте. Простая смена стратегии на старых данных отклоняется.
Глобальные reading.id выделяет последовательность Primary; это зависимость записи от Primary.
ID reading_cards локальны и не являются глобальным адресом.

процентов не стали; это важный результат анализа текущего seed.

## 5. Расчёт 3 → 4 на тех же данных

| Стратегия | Всего | Меняют узел | Остаются | Перенос |
|-----------|------:|------------:|---------:|--------:|
| hash % N | 100000 | 100000 | 0 | **100%** |
| Consistent (100 vnode) | 100000 | 50000 | 50000 | **50%** |

Modulo меняет делитель; оба ключа меняют остаток. В кольце только user 2 перехватывается
новым узлом. Ожидания 75%/25% относятся к большому множеству равномерных ключей,
а не к этому двухключевому набору. SQL рядом с отчётом считает вклад реальных readings;
складываются числители/знаменатели, не локальные проценты.
Физическая миграция 3→4 не выполнялась: задание требует расчёта объёма перемещений.

## 6. Кольцо и дальнейшие изменения

Virtual nodes обычно уменьшают разброс размеров дуг, но не делят один горячий ключ.
При добавлении пятого узла ожидается около 1/5 перемещений для равномерного пространства;
на нашем малом множестве ключей доля может отличаться. Удалённый узел отдаёт ключи следующим
точкам. Сначала копируют и сверяют данные: кольцо само ничего не переносит и не восстанавливает.
Временный отказ не повод исключать узел из кольца: нужны его реплика/failover или восстановление.

## 8. Итог (7 предложений)

Шард — отдельная БД с частью гаданий сервиса.
Shard key user_id сохраняет историю пользователя на одном узле.
Router выбирает подключение по этому ключу при чтении и записи.
Modulo прост, но смена делителя здесь переместит все строки.
Consistent Hashing сохраняет старые точки и уменьшил перенос до 50%.
Два ключа не загружают равномерно три узла даже при 100000 строках.
При росте аудитории я выбрал бы кольцо по user_id с репликами, мониторингом горячих ключей
и отдельным протоколом миграции.
