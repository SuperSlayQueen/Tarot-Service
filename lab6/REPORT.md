# Лабораторная работа №6
# Backend после шардирования

Проект: Tarot Reading Service, `C:\Users\Ardor\Desktop\c_labs`.
Результаты получены на PostgreSQL/HTTP, не в Python-модели.
Набор: 100000 readings и 100000 reading_cards, два пользователя seed сервиса.

## 1. Архитектура

Backend → ReadingService → ShardedReadingRepository → Router(user_id) → PostgreSQL 0/1/2.
Primary хранит пользователей, справочники, авторизацию и последовательность reading.id.
readings/reading_cards совместно размещены на шардах, с локальным FK и каскадным удалением.
Справочники не копируются: названия объединяются с гаданиями в backend.
По умолчанию Sharding выключен, сохранён режим Primary/Replica лаб 1–4.
Modulo: user 1 → shard 1, user 2 → shard 2; consistent: наоборот.

## 2. Single-shard query

`GET /api/reading?userId=1&pageSize=3` использует WHERE user_id=@UserId.
GetByUserIdAsync/GetPagedAsync выбирают один шард до SQL. В обоих режимах:
total=50000, все строки user 1; на остальных шардах этих readings нет.
Имена читаются из Primary: один шард гаданий не исключает зависимости от Primary.
GET/PUT/DELETE по одному reading.id не содержат shard key: поиск обращается ко всем узлам.
Альтернатива — каталог id→user_id/shard или составной адрес API; здесь их нет.

## 3. Агрегация

`GET /api/stats/readings-by-status`: локальные GROUP BY status/COUNT, затем сумма
в ShardedStatsRepository. Передаются агрегаты, не все строки.

| Modulo узел | NEW | COMPLETED | CANCELLED | Всего |
|-------------|----:|----------:|----------:|------:|
| 0 | 0 | 0 | 0 | 0 |
| 1 | 16667 | 16666 | 16667 | 50000 |
| 2 | 16667 | 16667 | 16666 | 50000 |
| API | 33334 | 33333 | 33333 | 100000 |

В consistent части меняются местами, итог тот же. Один узел не даст полный ответ.
Координатор — backend; Task.WhenAll выполняет запросы параллельно. Время примерно
max(T_i)+сеть+merge: рост N может ускорить локальную работу, но увеличить накладные расходы.
AVG объединяют через сумму/количество; DISTINCT суммируется только для непересекающихся
множеств с глобально уникальным ID. Универсальной границы масштабирования нет.

## 4. JOIN

Исходный GetDeckUsageAsync использовал decks→cards→reading_cards→readings.
Теперь decks/cards на Primary, факты на шардах. Обычный JOIN одного PostgreSQL не видит
другой экземпляр без FDW или координатора. Backend передаёт небольшое соответствие
card_id→deck_id как массивы; JOIN unnest с reading_cards/readings и DISTINCT выполняются
локально. Объединяются счётчики; количество справочных cards берётся только один раз.
Корректность требует уникальных reading.id и отсутствия дубликатов фактов между шардами.

Проверено: deck-usage → Rider-Waite, cardsCount=7, readingsCount=100000;
spread-stats → оба шаблона по 50000 гаданий, avgCardsPerReading=1.
Колокация дочерних карт по родительскому user_id сохраняет локальный JOIN и транзакцию.
Межсерверных FK на справочники и общего снимка всех БД нет.

## 5. ORDER BY + LIMIT

GetPagedAsync берёт page*pageSize кандидатов с каждого нужного шарда, сортирует объединение
и применяет глобальные Skip/Take. Полный порядок — created_at+id или status+id.
SQL COLLATE C и Ordinal согласованы для используемых ASCII-статусов.
Страница ограничена 1000 строками, глубина — 100000 кандидатов на шард.

HTTP `GET /api/reading?pageSize=20`: total=100000, ID 1000000000…1000000019.
Каждый непустой modulo-шард даёт лишь 10 из этих 20 строк: локальный top-20 не равен
глобальному. В consistent результат сохранён. Первые 100 строк одного узла также пропускают
свежие строки других. OFFSET нельзя завершать независимо на каждом узле.
Keyset с курсором (created_at,id) предпочтительнее для глубокой пагинации, но пока не реализован.
Count и страница — разные запросы, при конкурентной записи снимок не гарантирован.

## 6. Отказ шарда

Выполнен stop shard2 в modulo и восстановление:
- user 1 (живой shard1): HTTP 200;
- user 2 (shard2): HTTP 503;
- глобальная статистика: HTTP 503, не частичные цифры с кодом 200;
- после pg_isready и повторного запроса total=100000.
Недоступны 50000 гаданий и 50000 карт user 2. Справочные операции могут работать
при доступности Primary и остальных собственных зависимостей.

Timeout подключения/команд ограничен; middleware переводит временную ошибку шарда в 503.
Кольцо при отказе не меняется. Поиск по id и ответ после POST читают все шарды:
POST может сохраниться, а последующее чтение ответа упасть из-за другого узла.
Для production нужны идемпотентность и адресное повторное чтение.
Circuit breaker, реплики каждого шарда, failover, outbox и общая readiness шардов не реализованы:
это меры повышения отказоустойчивости. /health проверяет исходные зависимости, не все шарды.
Исключение упавшего узла из кольца без его данных не восстанавливает доступ.

## 7. Hot shard

Два ключа уже дают перекос 0/50000/50000. Даже равные строки не означают равный QPS:
популярный пользователь может создавать 75% запросов или более дорогие запросы.
Причины: малое разнообразие ключей, разные размеры историй, крупный tenant,
частая аналитика и выгрузки без LIMIT. Это анализ сценария, не измерение QPS.
Нужны мониторинг latency/QPS/IO, кэш лент, ограничения частоты и реплики чтения.
Virtual nodes не делят один горячий ключ; выделение/дробление tenant меняет модель доступа.

## 8. Анализ ключа и вывод

Плюсы user_id: локальная история и запись с картами, ключ известен заранее.
Минусы: глобальные статистика/лента и доступ по id распределены, горячий пользователь
не делится между узлами. Для пользовательского сервиса ключ оставил бы, но на двух
пользователях исходная Primary/Replica проще и достаточна.

| Операция | Сложность |
|----------|-----------|
| JOIN | Обмен справочниками, нет межсерверных FK |
| Агрегация | Частичные результаты, корректные AVG/DISTINCT |
| ORDER BY | Слияние, глубокая пагинация, согласованность |
| Миграция | Версии схем, копирование, сверка, переключение маршрута |
| Backup | Все шарды + Primary + конфигурация и генератор ID |
| Восстановление | Согласованная точка и сверка ссылок |
| Балансировка | Горячие ключи и нагрузка, не только строки |
